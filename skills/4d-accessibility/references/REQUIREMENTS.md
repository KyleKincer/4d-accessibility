# Requirements for full 4D application accessibility

Research date: September 23, 2026. This document defines the target and acceptance tests. It does not describe a completed implementation.

The target is complete access to the application's interface through macOS accessibility: reading meaningful content, navigating forms, operating controls, editing data, recovering from errors, and finishing workflows. Apple's current VoiceOver criteria require common tasks to work without sighted assistance and call for custom controls to provide accessibility equivalent to native controls. Selecting two visible invoice rows proves a much smaller capability. [Apple VoiceOver evaluation criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/voiceover-evaluation-criteria).

Read [current status](STATUS.md) for implementation coverage. Remaining gaps against this target are unfinished work.

## Which guidance applies

AppKit's public accessibility APIs and actual macOS assistive-technology behavior define the native implementation contract. For custom drawing, Apple provides `NSAccessibilityElement`, role-specific protocols, parent/child relationships, and change notifications. A matching role alone supplies only the minimum interface; additional behavior must reflect what the control actually does. [Apple custom-control guide](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html).

Use WCAG 2.2 A and AA outcomes as an additional quality benchmark. WCAG is a web standard; W3C's WCAG2ICT explains how its criteria apply to non-web software and is informative guidance, not a separate conformance standard. This plan does not claim WCAG certification or legal compliance. [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [WCAG2ICT scope](https://www.w3.org/WAI/standards-guidelines/wcag/non-web-ict/).

WAI-ARIA Authoring Practices supplies useful interaction designs for grids, dialogs, tabs, and menus. Its DOM roles, one-based ARIA row indexes, and browser key conventions are not AppKit APIs. Transfer the behavior and information requirements, then implement and test the native equivalent. ARIA itself does not implement keyboard behavior, and W3C requires testing the relevant browser and assistive-technology combinations. The same separation between semantics and working behavior matters here. [APG introduction](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/).

## Requirements and acceptance matrix

These are project acceptance requirements derived from the cited guidance. The checks are proposed tests, not results. Apply each row to every applicable control family and workflow.

| Capability | Native implementation and acceptance requirement | Evidence required |
| --- | --- | --- |
| Complete form discovery | Expose meaningful text and interactive objects under the real application/window tree. Include repeated and nested subforms, generated controls, and transient UI. Keep decorative objects out. An inactive page must have an accessible way to activate it. Apple requires complete, logical VoiceOver navigation through visible UI. [VoiceOver criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/voiceover-evaluation-criteria). | Compare the live form inventory with the AX tree. Every omission has an explicit decorative, inactive, or native-provider reason. Traverse forward and backward without skipped objects or cycles. |
| Native children and relationships | Preserve working AppKit accessibility. Add custom elements to their actual parent rather than replacing the existing tree. Standard controls already implement properties, actions, and notifications. [AppKit protocol overview](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol), [custom element attachment](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html). | Native window controls, menus, text editors, and embedded content remain reachable and operable. No duplicate representation of the same control. Parent/child links agree in both directions. |
| Names, roles, values, and states | Supply truthful localized labels, roles, values, enabled/read-only/selected/expanded states, and supported actions. Keep label and value separate. Include visible label text in the accessible name so voice users can address what they see. [Name, role, value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html), [label in name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html). | Read every supported state through an external AX client. Inspect labels without surrounding visual context. Do not expose an editable role or setter for a read-only value. |
| Keyboard focus | Implement real focus readback and a working focus setter for controls that accept keyboard focus. `isAccessibilityFocused` describes keyboard focus; publishing a Boolean cannot move it. Use a control adapter that changes actual 4D focus and confirms it. [AppKit focus setter](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/setaccessibilityfocused(_:)). | Focus through AX, type through the normal keyboard path, and verify the intended control receives input. Test Tab and Shift-Tab between controls and into/out of composites. Selection, VoiceOver cursor, and keyboard focus must remain distinguishable. [APG keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/). |
| Focus visibility and geometry | Return current screen-space geometry and reveal the item receiving focus. Clipping, window movement, zoom, scroll offsets, and display changes must not leave the focused control hidden or mislocated. [AppKit frame contract](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol), [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html). | Inspect and hit-test after resizing, scrolling, nested subform clipping, and moving between displays of different scale. A focus change must produce a usable on-screen target. |
| Buttons, toggles, and value controls | Implement role-appropriate activation and setters, including checkbox/radio state and slider/stepper limits. Native controls should retain their existing implementation; custom controls need equivalent behavior. [Apple custom-control roles](https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/ImplementingAccessibilityforCustomControls.html). | AX activation and ordinary activation reach the same guarded application behavior exactly once. Disabled controls refuse changes. Values and dependent UI agree after success or rejection. |
| Text reading and editing | Support text value, selection/caret range, selected text, and the range/geometry queries needed by the editor. AppKit provides these separately from whole-value replacement. Preserve the native editor where possible. [Selected text range](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilityselectedtextrange()), [text range geometry](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilityframe(for:)). | Read and select text; replace part of it; commit, reject, cancel, and undo through ordinary application behavior. Cover multiline and Unicode text. Confirm accessible speech/selection and the actual editor agree. Protect secure-entry content. |
| Scrollable and virtualized content | Keep logical contents distinct from visible contents. Native tables have separate rows and visible rows; scroll views expose scroll bars. A bounded viewport cache must still permit reaching remaining content. [AppKit table](https://developer.apple.com/documentation/appkit/nsaccessibilitytable), [vertical scroll bar](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilityverticalscrollbar()). | Starting at the first page, use standard AX/VoiceOver controls to reach and act on the middle and final rows, then return. Repeat horizontally. No mouse, screenshots, or private bridge request may be necessary to cross a cache boundary. |
| Table structure and selection | Publish actual columns, headers, cells, selection, logical indexes, and counts. Keep row selection separate from cell activation. AppKit exposes headers, selected rows, and indexed cell access. [Table protocol](https://developer.apple.com/documentation/appkit/nsaccessibilitytable), [cell lookup](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilitycell(forcolumn:row:)). | Read each visible column with its header, select multiple rows, and preserve record identity after sort/filter/reload. A concatenated summary may supplement the table but cannot replace independently operable cells. |
| Table sorting and editing | Expose sort state and a working header action where sorting exists. Represent editable cells and their editing lifecycle. Navigation and in-cell editing need distinct behavior so arrow keys can serve each purpose. [AppKit sort direction](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilitysortdirection()), [APG grid editing](https://www.w3.org/WAI/ARIA/apg/patterns/grid/). | Sort through the accessible header and verify order/state. Enter, edit, validate, commit, cancel, and leave a cell without bypassing callbacks. Test cell buttons, checkboxes, and popups where the grid provides them. |
| Hierarchy | Use outline/tree relationships, disclosure level, expanded state, and expansion/collapse behavior for hierarchical data. AppKit provides an outline protocol and disclosed-row relationships. [AppKit outline](https://developer.apple.com/documentation/appkit/nsaccessibilityoutline), [disclosed rows](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilitydisclosedrows()), [APG treegrid](https://www.w3.org/WAI/ARIA/apg/patterns/treegrid/). | Navigate parent/child/sibling relationships, expand and collapse, and restore focus when a focused descendant disappears. A hierarchy cannot be flattened into unlabeled rows and counted as supported. |
| Popups, comboboxes, menus, and tabs | Preserve native semantics or implement equivalent open, choose, dismiss, selected-state, and child relationships. AppKit offers menu actions; APG documents selection and popup behavior, and tab-to-panel relationships. [AppKit show menu](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilityperformshowmenu()), [combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [menus](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/), [tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/). | Operate every choice using AX and keyboard/VoiceOver. Open a context menu without a pointer. Switch every tab and reach its content. Dismiss transient UI and restore a useful focus position. |
| Dialogs and modal state | Move focus into an opened modal dialog, expose its title and controls, prevent interaction with inactive background content, and restore useful focus when it closes. [AppKit modal state](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/isaccessibilitymodal()), [APG modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). | Open, read, accept, cancel, and close both application and validation dialogs. Test nested dialogs and replacement of the invoking control. Background actions must not mutate the application during modality. |
| Errors and dynamic changes | Expose the invalid input and explanatory error text. Announce relevant status changes without forcing focus to ordinary status text. Native notifications include value, focus, selection, row-count, layout, creation/destruction, and announcements. [Error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html), [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [AppKit notifications](https://developer.apple.com/documentation/appkit/nsaccessibility-swift.struct/notification). | Observe notifications through an external AX observer. Validate an error, correct it, and continue. Sorting, lazy loading, record switches, and generated-child replacement must not leave a stale cursor or produce constant repeated announcements. |
| Rich and embedded content | Keep an embedded native/web accessibility tree when it works. Provide equivalent information and operations for custom images, charts, drag/drop, or other nonstandard interactions. [Apple VoiceOver guidance](https://developer.apple.com/design/human-interface-guidelines/voiceover), [WCAG non-text content and dragging](https://www.w3.org/TR/WCAG22/). | Exercise the actual embedded content, including navigation back to the host form. Expose chart meaning and accessible alternatives to pointer-only operations. A label on an otherwise opaque web/plugin area is insufficient. |

## Virtualization must preserve navigation

Full accessibility does not require eagerly materializing every row and cell. W3C explicitly supports partial table rendering with total counts and logical indexes. The transferable requirement is that the accessibility model describe the real data set accurately. AppKit likewise distinguishes `accessibilityRows` from `accessibilityVisibleRows`, and provides indexed cell queries. These APIs are not interchangeable with ARIA's DOM attributes. [APG partial tables](https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/), [AppKit table](https://developer.apple.com/documentation/appkit/nsaccessibilitytable), [indexed cell access](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilitycell(forcolumn:row:)).

For this bridge, the recommended design is a bounded cache over a complete logical collection. Keep stable row keys and logical indexes, obtain additional rows/cells on demand, and provide working reveal/scroll operations. Preserve selection and reading position as the cache changes. Hidden tab panels and collapsed descendants are different from uncached rows: users must activate their tab or expand their parent before interacting with that content. This is a design inference from the APIs and interaction patterns above, subject to live VoiceOver validation.

Do not advertise a 20-row table when the user is browsing 600 rows. Do not publish fabricated onscreen bounds for an offscreen row. Do not make all rows unavailable because a fixed snapshot/node limit is exceeded. A resource limit is an implementation constraint; the acceptance test remains successful navigation and action across it.

Check availability before selecting a native reveal API. Apple's SDK on this machine declares `NSAccessibilityScrollToVisibleAction` as available starting with macOS 26.0 in `AppKit.framework/Headers/NSAccessibilityConstants.h`. The inspected `NSAccessibilityProtocols.h` does not declare a general `accessibilityPerformScroll...` method. For older supported systems, validate a public scroll-bar/focus implementation rather than inventing an AppKit selector. This SDK observation does not prove how VoiceOver will use the action. The scroll-bar contract is documented separately. [AppKit vertical scroll bar](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol/accessibilityverticalscrollbar()).

## Keep host changes small by moving responsibility into adapters

The following is an architecture recommendation, not an Apple or W3C API requirement. It follows Apple's preference for retaining standard control behavior and supplementing custom controls.

1. Attach once per root form through the common form-opening path. Keep scheduling, cleanup, form generations, subform recursion, and native notifications in the reusable integration. Generate the mechanical compiler declarations and instrumentation.
2. Discover supported standard controls from live form metadata by default. Use the runtime type, existing visible title, state, value, page, focus, and geometry. A basic labeled form should not require a handwritten list of every button and field.
3. Prefer an existing native AX implementation before adding a proxy. If a proxy is necessary, one reusable adapter should implement the control family's discovery, state, actions, focus, and editing semantics.
4. Register third-party grids by area/binding once. Put row loading, cell formatting, headers, geometry, selection, scrolling, and editing in the vendor adapter. Each instance still needs private state and verified stable identity.
5. Reserve overrides for information the runtime cannot determine: an icon's meaning, ambiguous field labels, application-specific relationships, safe custom actions, business validation, and custom drawing. Keep overrides declarative where possible; permit a callback for behavior.
6. Route AX actions through the same validated command or editing path used by ordinary input. Maintain application permissions, event ordering, transaction behavior, and unsaved edits. Do not require developers to maintain an independent business-logic implementation for accessibility.
7. Emit coverage diagnostics for every unsupported or ambiguous object. An explicit failure is safer than fabricated semantics during development, but silently omitting an ordinary active control is not completion. Track discovery, reading, and each action separately.

The bridge cannot reliably infer the intent of arbitrary drawing or an icon without a label. It also cannot infer the consequences of a custom handler, stable identity from duplicate display text, or validation/commit semantics from a writable data binding. The current research found no documented universal 4D plugin hook that supplies every control and lifecycle automatically. Common form infrastructure plus reusable adapters can reduce host edits; claiming an install-only solution needs additional evidence. Apple's distinction between informational properties and executable actions also makes clear why publishing metadata alone cannot provide complete interaction. [AppKit overview](https://developer.apple.com/documentation/appkit/nsaccessibilityprotocol).

## Evidence required before calling the solution complete

Accessibility Inspector can inspect properties, actions, and navigation and find common issues. Apple explicitly says a clean audit does not guarantee an accessible app and requires assistive-technology testing as well. Use both. [Accessibility Inspector](https://developer.apple.com/documentation/accessibility/accessibility-inspector), [Apple audit guidance](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app).

The project should record these acceptance gates:

- Every active form/control family has a coverage inventory with working native ownership or a tested adapter. Include conditional, empty, loading, error, read-only, modal, and permission-restricted states.
- An external client starting from the process/window AX tree can discover controls, inspect supported actions, act, and confirm the application result. Bridge-private test methods may verify effects but cannot provide the missing interaction path. This is the project's AI-agent acceptance criterion.
- Keyboard-only and VoiceOver-only users can complete representative entire workflows. Include a simple edit form; an invoice with all columns and actions; a long editable grid; nested/repeated/replaced subforms; a hierarchy; and generated-form builders. Complete forward/backward traversal and the matrix's error-recovery tests.
- Test Voice Control and Switch Control on representative custom controls. VoiceOver success is useful evidence but does not prove another assistive technology's interaction model. Apple recommends evaluating Voice Control after VoiceOver. [Apple evaluation guidance](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/voiceover-evaluation-criteria).
- Each asynchronous action confirms actual state or reports rejection. Test stale references after sorting, closing, reopening, changing records, and replacing children. Never equate transport acceptance with completed business behavior. This gate follows the bridge's existing receipt and identity design.
- Record versions, package/source hashes, execution mode, relevant data size, latency, and an AX/notification trace. Compare human and AX behavior where events or validation matter. Real application workflows need their own non-production evidence; synthetic rows do not establish them.
- Repeat on each supported macOS/4D/vendor/runtime combination. Windows requires its own provider and runtime accessibility evidence; Windows source compilation cannot prove macOS AX behavior or Windows accessibility.

An AX bridge also cannot establish full product accessibility by itself. Contrast, text resizing, color independence, motion, captions, and other visual/audio interaction concerns require UI and content work beyond the tree. Audit those separately against Apple's design guidance and the selected WCAG2ICT benchmark. [Apple accessibility HIG](https://developer.apple.com/design/human-interface-guidelines/accessibility), [WCAG2ICT scope](https://www.w3.org/WAI/standards-guidelines/wcag/non-web-ict/).

Completion means the applicable requirements pass with the real application, and the reusable adapters make equivalent support practical for other 4D hosts. A smaller implementation can be released as partial support, but its unsupported control families and workflows must remain explicit.
